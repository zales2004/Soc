## 1. What is a log?

A **log** is a timestamped record generated by an operating system, application, network device, security product, or cloud service. It records activity, state changes, errors, and other operational or security-relevant information.

Think of logs as the activity history of a digital system. They help an analyst reconstruct what happened, when it happened, which account or device was involved, and what evidence supports a conclusion.

### 1.1 Example of a simplified security log

```text
Timestamp: 2026-11-04 10:30:15
Host: WIN-CLIENT-01
Username: administrator
Event: Failed logon
Source IP: 192.0.2.25
Result: Failure
```

An analyst can use this record to ask:

- Which account was targeted?
- Which system recorded the event?
- When did it occur, and in which time zone?
- Where did the connection originate?
- Was the attempt successful or unsuccessful?
- Were there other related events before or after it?

The example IP address `192.0.2.25` belongs to a documentation-only address range. It is not a real threat indicator.

### 1.2 Why logs matter in a SOC

A Security Operations Center (SOC) uses logs to:

1. Detect suspicious or unauthorized activity.
2. Investigate security alerts.
3. Reconstruct timelines.
4. Identify affected users, endpoints, servers, and services.
5. Correlate activity across different systems.
6. Validate whether an alert represents a real security incident.
7. Preserve evidence and support incident response.
8. Identify gaps in monitoring and improve detections.

**Core principle:** A log is evidence of a recorded event. It is not automatically proof of malicious intent.

## 2. Essential terminology

These terms are related but should not be treated as interchangeable.

| Term | Meaning | Example |
|---|---|---|
| Log | A record or message generated by a system | An authentication record |
| Event | An occurrence on a system | A user signs in |
| Telemetry | Observable data about system, user, application, or network activity | Process, file, and network activity |
| Alert | A notification generated when detection logic identifies activity of interest | 30 failed logins in five minutes |
| Incident | A suspected or confirmed security matter requiring investigation or response | Unauthorized account access |
| IOC | Indicator of Compromise | A known malicious hash or domain |
| TTP | Tactics, Techniques, and Procedures | Credential access or lateral movement |
| Correlation | Linking related records using time, identity, host, IP, process, or other context | Failed logins followed by a successful login |
| Triage | Initial assessment of an alert's validity, priority, and next steps | Checking source, account, and evidence |
| Enrichment | Adding useful context to an event | Asset owner or threat-intelligence context |

### 2.1 Event vs alert vs incident

Consider this sequence:

- **Event:** A user enters an incorrect password.
- **Alert:** A detection identifies repeated failed logins against an account.
- **Incident:** Investigation establishes that an unauthorized person accessed the account.

An alert is not automatically an incident. A SOC analyst validates the underlying events, checks context, and follows the organization's incident-handling process.

### 2.2 What makes a log useful?

A useful security record often contains:

- Timestamp and time zone
- Event identifier or event type
- Hostname or device identifier
- Username or account identifier
- Source and destination addresses, when applicable
- Action or operation
- Outcome or status
- Process, service, or application details
- Additional event-specific fields

Not every log contains every field. Missing fields should be treated as a visibility limitation, not filled in by assumption.

## 3. Major categories of security logs

Different systems record different parts of an organization's activity.

| Log category | What it records | SOC investigation value |
|---|---|---|
| Authentication / identity | Logins, failures, MFA, account changes | Brute force, password spraying, account compromise |
| Operating system | Services, startup, system errors, configuration | System changes and suspicious activity |
| Endpoint / EDR | Process, file, registry, network, and detection events | Malware, execution, persistence, containment |
| Network | Connections, flows, routing, traffic metadata | Scanning, command-and-control, lateral movement |
| Firewall | Allowed and blocked connections | Connection attempts and policy violations |
| DNS | Domain queries and responses | Suspicious domains and possible command-and-control |
| Proxy / web gateway | Web requests, URLs, users, actions | Phishing, malicious downloads, web activity |
| VPN | Remote access sessions and authentication | Unusual remote access and account misuse |
| Email security | Message delivery, attachments, URLs, verdicts | Phishing and malicious attachments |
| Application | Application access, errors, administrative actions | Application abuse and suspicious changes |
| Cloud audit | Sign-ins, API calls, administrative changes | Cloud account misuse and configuration changes |
| Database | Queries, authentication, privilege changes | Unauthorized data access |

### Example: correlating multiple log sources

An employee account has repeated failed logins. A useful investigation might examine:

1. Identity logs for the account and authentication outcome.
2. VPN logs for remote access sessions.
3. Endpoint logs for activity on the user's device.
4. DNS and firewall logs for related network connections.
5. EDR telemetry for suspicious process execution.

No single source necessarily tells the whole story. Correlation builds a more complete picture.

## 4. Windows Event Logs

Windows records operating-system and security activity in event channels. Analysts commonly inspect these records using **Event Viewer**.

### 4.1 Open Windows Event Viewer

1. Press `Win + R`.
2. Enter `eventvwr.msc`.
3. Press Enter.
4. Expand **Windows Logs**.
5. Select **Security**, **System**, or **Application** as required.

The main Windows Logs channels include:

| Channel | Purpose |
|---|---|
| Application | Events generated by applications |
| Security | Authentication, account management, and audited security activity |
| System | Operating-system components, drivers, and services |
| Setup | Installation and setup-related events |
| Forwarded Events | Events forwarded from other computers |

For SOC investigations, the **Security** channel is particularly important.

### 4.2 Understand the structure of a Windows event

A Windows event commonly includes:

- **Log Name:** The channel where the event was recorded.
- **Source / Provider:** The component that generated the event.
- **Event ID:** Identifier for the event type.
- **Level:** Information, Warning, Error, or another severity level.
- **Date and Time:** When the event was recorded.
- **Computer:** The host that generated the event.
- **User:** User context, where applicable.
- **Event details:** Structured fields and descriptive information.

In Event Viewer, open an event and inspect both the **General** and **Details** tabs. The XML view can expose structured fields that are not obvious in the General description.

### 4.3 Important Windows Security Event IDs

These Event IDs are valuable for entry-level SOC investigations. Memorize the meaning, but always inspect the event fields and surrounding activity.

#### Authentication and logon events

| Event ID | Meaning | SOC relevance |
|---|---|---|
| 4624 | An account was successfully logged on | Investigate unusual access and successful authentication |
| 4625 | An account failed to log on | Investigate password guessing, spraying, and failed access |
| 4634 | An account was logged off | Understand session termination |
| 4647 | User initiated logoff | User-initiated session termination |
| 4648 | A logon was attempted using explicit credentials | Investigate alternate credential use |
| 4672 | Special privileges assigned to a new logon | Review privileged logon context |
| 4740 | A user account was locked out | Investigate repeated authentication failures |
| 4768 | Kerberos authentication ticket (TGT) requested | Domain authentication investigation |
| 4769 | Kerberos service ticket requested | Investigate access to domain services |
| 4771 | Kerberos pre-authentication failed | Investigate Kerberos authentication failures |
| 4776 | Domain controller attempted to validate credentials using NTLM | Investigate NTLM authentication activity |

#### Account and group-management events

| Event ID | Meaning | SOC relevance |
|---|---|---|
| 4720 | User account created | Detect unexpected account creation |
| 4722 | User account enabled | Investigate unexpected account activation |
| 4724 | An attempt was made to reset an account password | Review password administration |
| 4725 | User account disabled | Investigate account changes |
| 4726 | User account deleted | Review unexpected account deletion |
| 4728 | Member added to a security-enabled global group | Investigate global group membership changes |
| 4729 | Member removed from a security-enabled global group | Review group membership changes |
| 4732 | Member added to a security-enabled local group | Investigate local group privilege changes |
| 4733 | Member removed from a security-enabled local group | Review local group membership changes |

#### Process and service events

| Event ID | Meaning | SOC relevance |
|---|---|---|
| 4688 | A new process was created | Investigate execution and command lines |
| 4697 | A service was installed on the system | Investigate possible service-based persistence |

**Important distinction:** Event ID 4728 concerns a security-enabled **global** group. Event ID 4732 concerns a security-enabled **local** group. Do not confuse these during investigations.

**Audit policy caveat:** Event availability depends on the relevant Windows audit policy, system role, configuration, and event collection. For example, process command-line details in Event 4688 require the appropriate process-creation command-line auditing policy. An event may not exist in your lab if the relevant auditing is not enabled or the activity has not occurred.

## 5. Windows logon types

A logon type helps describe how a Windows logon occurred. It is especially useful when investigating Event ID 4624 or 4625.

| Logon Type | Meaning | Example |
|---|---|---|
| 2 | Interactive | User signs in at the local keyboard and screen |
| 3 | Network | Access to a resource over the network |
| 4 | Batch | Scheduled or batch job |
| 5 | Service | Service starts under an account |
| 7 | Unlock | User unlocks an existing session |
| 8 | NetworkCleartext | Network logon using credentials presented in a form that may be passed to an authentication package in clear text |
| 9 | NewCredentials | Process uses alternate credentials for outbound connections |
| 10 | RemoteInteractive | Remote Desktop / Terminal Services interactive logon |
| 11 | CachedInteractive | Interactive logon using cached domain credentials |

### 5.1 Logon Type 2 — Interactive

A user signs in directly at the machine.

**Investigation question:** Is this local sign-in expected for the account and device?

### 5.2 Logon Type 3 — Network

A user or service accesses a resource over the network. This does not necessarily mean Remote Desktop.

**Investigation question:** Which source system accessed the destination, and which resource was accessed?

### 5.3 Logon Type 5 — Service

A service logs on using its configured account.

**Investigation question:** Is the service account expected, and is the service configuration legitimate?

### 5.4 Logon Type 10 — RemoteInteractive

An interactive remote session, commonly associated with Remote Desktop Services / RDP.

**Investigation question:** Was remote access expected for this account, host, source, and time?

A logon type alone does not establish whether activity is malicious. Interpret it with the account, source address, destination host, authentication context, and surrounding events.

## 6. Investigating common Windows events

### 6.1 Event ID 4624 — Successful logon

A successful logon event records that an account was successfully authenticated.

Illustrative fields:

```text
Event ID: 4624
Target Account: administrator
Logon Type: 10
Source Network Address: 192.0.2.25
Computer: WIN-SERVER-01
```

Questions for the analyst:

- Is the account authorized to access this host?
- Is the source address expected?
- Is the logon type normal for this user?
- Was the login at an unusual time?
- Is there a related VPN, MFA, or endpoint event?
- What activity occurred after the login?

### 6.2 Event ID 4625 — Failed logon

This event records an unsuccessful logon attempt.

Illustrative fields:

```text
Event ID: 4625
Target Account: administrator
Logon Type: 3
Source Network Address: 192.0.2.50
Status: Authentication failure
```

Possible explanations include:

- User entered an incorrect password.
- A service or scheduled task has outdated credentials.
- A password-guessing attempt occurred.
- An attacker attempted password spraying.
- A system or application is misconfigured.

Do not label one failed login as a brute-force attack. Look for repetition, distribution across accounts, source patterns, timing, and related successful logons.

Useful 4625 fields can include:

- Target account name and domain
- Logon type
- Workstation name
- Source network address and port
- Status and SubStatus
- Authentication package
- Failure information

Status and SubStatus values help explain why authentication failed. Interpret them using Microsoft's event documentation and the actual event details.

### 6.3 Event ID 4688 — Process creation

This event records creation of a new process when process-creation auditing is enabled.

Illustrative example:

```text
Event ID: 4688
New Process Name:
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe

Creator Process:
C:\Windows\explorer.exe
```

This can help answer:

- Which process was started?
- Which process launched it?
- Which account executed it?
- What command line was used, if captured?
- Was the execution expected for that host and user?

Attackers may abuse legitimate operating-system tools, a behaviour often called **living off the land**. PowerShell, cmd.exe, scripting engines, and administrative utilities can be used for both legitimate and malicious purposes.

Examples that may deserve investigation include:

- Office applications spawning command interpreters.
- Encoded or heavily obfuscated PowerShell commands.
- Unexpected script execution by a service account.
- A process launching from a suspicious temporary directory.
- Unusual parent-child process relationships.

A process name alone is not enough to determine maliciousness. Examine the command line, parent process, user, file path, hash, signature, network activity, and surrounding telemetry.

### 6.4 Event ID 4720 — User account created

Illustrative example:

```text
Event ID: 4720
New Account: support_backup
Subject Account: administrator
```

Investigate:

- Who created the account?
- Was the account creation approved?
- Is the account name consistent with organizational naming?
- When was the account created?
- Was it subsequently enabled or added to a privileged group?
- Did the new account sign in?

### 6.5 Event ID 4728 / 4732 — Group membership changes

An unexpected group membership change can affect privileges.

- **4728:** Member added to a security-enabled global group.
- **4732:** Member added to a security-enabled local group.

Investigate the subject account that performed the change, the member account added, the target group, the host, the timestamp, and whether the change was authorized.

## 7. Linux logs and authentication monitoring

Linux systems record authentication, system, service, and kernel activity. The exact locations depend on distribution and logging configuration.

### 7.1 Common Linux log locations and tools

| Log / tool | Common purpose |
|---|---|
| `/var/log/auth.log` | Authentication messages on many Debian/Ubuntu systems |
| `/var/log/secure` | Authentication messages on many RHEL-family systems |
| `/var/log/syslog` | General system messages on many Debian/Ubuntu systems |
| `/var/log/messages` | General system messages on some distributions |
| `/var/log/kern.log` | Kernel messages on some distributions |
| `/var/log/audit/audit.log` | Linux Audit subsystem records, when configured |
| `journalctl` | Queries the systemd journal |

A file may not exist or may not contain the expected records if the system uses a different logging setup. Use the journal or the distribution's logging configuration when appropriate.

### 7.2 Understanding SSH authentication logs

SSH (Secure Shell) is commonly used for remote administration of Linux systems.

Illustrative failed-login record:

```text
Nov 04 10:20:15 ubuntu sshd[1234]:
Failed password for invalid user admin
from 192.0.2.50 port 54210 ssh2
```

Field interpretation:

| Field | Meaning |
|---|---|
| Nov 04 | Date |
| 10:20:15 | Time |
| ubuntu | Hostname |
| sshd | SSH daemon / service |
| 1234 | Process ID |
| Failed password | Authentication failure |
| invalid user admin | Username supplied was not a valid account |
| 192.0.2.50 | Source IP address |
| 54210 | Source port |
| ssh2 | SSH protocol version |

**SOC interpretation:** The SSH service recorded a failed authentication attempt using an invalid username from the specified source address.

Repeated failures may indicate password guessing or scanning, but also check for legitimate administrative activity, automation, and misconfiguration.

### 7.3 Useful Linux log-analysis commands

Run these commands on a Linux system you own or are authorized to investigate.

#### Read authentication logs

```bash
# View the authentication log, if present
sudo less /var/log/auth.log

# Display the latest 50 lines
sudo tail -n 50 /var/log/auth.log

# Display the latest 100 lines
sudo tail -n 100 /var/log/auth.log
```

#### Search for SSH failures and successes

```bash
# Find failed password messages
sudo grep -i "Failed password" /var/log/auth.log

# Find successful password authentication messages
sudo grep -i "Accepted password" /var/log/auth.log

# Find SSH daemon messages
sudo grep -i "sshd" /var/log/auth.log
```

#### Monitor activity in real time

```bash
# Follow new messages as they are written
sudo tail -f /var/log/auth.log
```

Press Ctrl+C to stop following the file.

#### Use the systemd journal

```bash
# Review recent system messages
sudo journalctl --since "1 hour ago"

# Review SSH service messages
sudo journalctl -u ssh --since today

# On some distributions, the service unit may be sshd
sudo journalctl -u sshd --since today
```

The SSH service unit name varies by distribution. Use the unit that exists on your system.

### 7.4 What to extract from a Linux authentication event

When reviewing an SSH event, identify:

- Timestamp and time zone
- Hostname
- Service name
- Account or username
- Source IP and source port
- Authentication result
- Whether the account exists
- Whether a successful login followed the failures

Also examine related sudo, account-management, service, and system events when relevant.

## 8. SOC investigation methodology: suspected brute-force activity

### Scenario

A monitoring system generates the following alert:

```text
Alert: Multiple Failed SSH Login Attempts
Target Host: Ubuntu-Server
Target Account: root
Source IP: 192.0.2.50
Failed Attempts: 45
Time Window: 5 minutes
```

This is an illustrative scenario. The values are not evidence from a real incident.

### Step 1 — Validate the alert

- Confirm the alert time range and time zone.
- Identify the source data and detection rule.
- Verify that the underlying raw events exist.
- Check whether the count and threshold are accurate.

### Step 2 — Identify the source and targeted accounts

Determine:

- Source IP address
- Target host
- Target account or accounts
- Number of failures
- First and last observed attempts
- Whether multiple accounts were targeted

One source targeting many accounts may suggest password spraying. Many attempts against one account may suggest password guessing or brute force. These are hypotheses to validate, not automatic conclusions.

### Step 3 — Check for successful authentication

Search for successful logins involving the targeted account and source address.

A successful login after repeated failures increases concern, but must still be validated. It may be unrelated or originate from a legitimate user behind shared infrastructure.

### Step 4 — Build a timeline

Record:

- First failed attempt
- Subsequent attempts
- Last failed attempt
- Any successful authentication
- Activity after authentication
- Related endpoint or network events

Use the original event timestamps and time zones. Do not confuse event time with SIEM ingestion time.

### Step 5 — Determine scope and impact

Ask:

- Was the account privileged?
- Was access actually obtained?
- Which host was involved?
- Was there suspicious activity after the login?
- Were other accounts or hosts affected?
- Is there evidence of persistence or lateral movement?

### Step 6 — Decide on severity and escalation

Severity depends on the evidence, asset criticality, account privileges, and organizational policy.

A failed-login pattern without successful access may be a lower-impact event than confirmed unauthorized access to a critical server. Follow the organization's severity matrix and escalation process.

### Step 7 — Document findings

A good investigation record separates:

- **Observed facts:** What the logs directly show.
- **Assessment:** What the evidence may indicate.
- **Unknowns:** What has not yet been established.
- **Actions:** What was done or recommended.
- **Next steps:** What further validation or escalation is required.

Do not claim that a system is compromised unless the evidence supports that conclusion.

## 9. How logs reach a SIEM

A SIEM centralizes telemetry from different systems so analysts can search, correlate, and investigate it.

### 9.1 Typical log-to-SIEM pipeline

```text
Windows / Linux / Firewall / DNS / EDR / Cloud
                    |
                    v
           Log Collection
       Agent / Forwarder / API / Syslog
                    |
                    v
           Parsing and Extraction
          Identify useful event fields
                    |
                    v
          Normalization and Enrichment
       Standardize fields and add context
                    |
                    v
             Storage / Indexing
                    |
                    v
           Search / Correlation
                    |
                    v
            Detection / Alert
                    |
                    v
          SOC Triage / Investigation
                    |
                    v
       Response / Escalation / Reporting
```

### 9.2 The stages explained

| Stage | What happens | Example |
|---|---|---|
| Collection | Data is moved from its source | A forwarder sends Windows Security events |
| Parsing | Fields are extracted from raw data | Extract username and source address |
| Normalization | Equivalent fields are mapped to a common structure | Map vendor-specific source IP fields to a standard field |
| Enrichment | Additional context is added | Add asset owner or user department |
| Indexing | Events are stored for search | Store events in a searchable index |
| Detection | Rules or analytics identify activity | Detect repeated failed logins |
| Investigation | Analyst validates and correlates evidence | Check whether a successful login followed failures |

**Splunk example:** Splunk Universal Forwarder can collect selected Windows Event Log channels or monitor selected files and forward data to Splunk. The forwarder is a collection and forwarding component; it is not the whole SIEM platform.

### 9.3 Why data quality matters

A detection can fail or produce misleading results if:

- A host stops sending logs.
- The required audit policy is disabled.
- Important fields are not extracted.
- Timestamps are incorrect.
- The source format changes.
- Events are delayed, duplicated, or dropped.
- The detection searches the wrong index or time range.

Analysts should validate the underlying data before trusting a detection result.

## 11. Common investigation patterns

| Pattern | What to look for | Important caution |
|---|---|---|
| Repeated failed logins | High failure count, same source, same account | Could be a user or service with outdated credentials |
| Password spraying | One source attempting multiple accounts | Validate time window and authentication context |
| Successful login after failures | Failure sequence followed by success | Success may be legitimate or unrelated |
| Unusual RDP access | Event 4624 with Logon Type 10 | Remote access can be normal for administrators |
| New account creation | Event 4720 | Confirm change authorization |
| Privileged group change | Event 4728 or 4732 | Confirm target group and change request |
| Suspicious process execution | Event 4688 and process telemetry | Process name alone is not proof of maliciousness |
| SSH brute-force suspicion | Repeated SSH authentication failures | Consider exposed services, automation, and source context |

## 12. Interview preparation

Use these questions for active recall. Try answering before reading the model answer.

### Fundamentals

**1. What is a log in cybersecurity?**  
A log is a record generated by a system, application, network device, or security product. It captures activity and provides evidence for monitoring and investigation.

**2. Why are logs important to a SOC analyst?**  
Logs help analysts detect suspicious activity, investigate alerts, correlate events, reconstruct timelines, identify affected assets, and document evidence.

**3. What is the difference between a log and an event?**  
An event is an occurrence, such as a login. A log is the record that documents that occurrence. In SIEM conversations, the terms are sometimes used loosely.

**4. Explain the difference between an event, alert, and incident.**  
An event records activity. An alert flags activity identified by detection logic. An incident is a suspected or confirmed security matter that requires investigation or response.

**5. Does every failed login indicate an attack?**  
No. Failed logins can result from user mistakes, expired passwords, misconfigured services, or malicious activity. Analysts assess frequency, source, target, timing, and surrounding evidence.

### Windows events

**6. What is Windows Event ID 4624?**  
It records a successful logon. Analysts examine the account, host, logon type, source address, and surrounding events.

**7. What is Windows Event ID 4625?**  
It records a failed logon. It can help investigate password guessing, spraying, and other authentication issues.

**8. What is the difference between Event IDs 4624 and 4625?**  
4624 records a successful logon; 4625 records a failed logon.

**9. What is Windows Event ID 4688?**  
It records process creation when the relevant auditing is enabled. It can help analysts investigate suspicious process execution and command lines.

**10. What is Windows Event ID 4720?**  
It records user account creation.

**11. What is the difference between Event IDs 4728 and 4732?**  
4728 records a member added to a security-enabled global group. 4732 records a member added to a security-enabled local group.

**12. What does Logon Type 3 mean?**  
It represents a network logon, such as accessing a network resource. It does not automatically mean an RDP session.

**13. What does Logon Type 10 mean?**  
It represents a RemoteInteractive logon, commonly associated with Remote Desktop Services.

**14. Why might Event ID 4688 be missing command-line information?**  
Process creation may be audited without command-line capture. The relevant process-creation command-line audit policy and event collection must be configured.

### Linux logs

**15. Where are authentication logs commonly found on Ubuntu?**  
Often in `/var/log/auth.log`. Systems using systemd journaling can also be investigated with `journalctl`.

**16. What is SSH?**  
Secure Shell is a protocol used for secure remote access and administration of systems.

**17. How do you search for failed SSH password attempts?**  
On a system using the Ubuntu authentication log, use `sudo grep -i "Failed password" /var/log/auth.log`. If logs are in journald, inspect the SSH service with `journalctl`.

**18. What does an SSH log entry containing “Accepted password” indicate?**  
It indicates that password authentication was accepted for the account shown. The analyst should still validate whether the access was expected.

### Investigation

**19. How would you investigate repeated failed logins?**  
Validate the alert, identify the source and target accounts, count attempts, examine the time range, check for successful authentication, correlate related activity, assess impact, and document findings.

**20. What is password spraying?**  
An attack pattern in which an actor tries a small number of likely passwords across many accounts, often to avoid triggering account-specific lockout thresholds.

**21. What is brute force?**  
Repeatedly attempting passwords or credentials against an account or service to gain unauthorized access.

**22. Why is time synchronization important in log analysis?**  
It helps analysts accurately order and correlate events from different systems. Incorrect clocks and time zones can create misleading timelines.

**23. What should a SOC analyst do when expected logs are missing?**  
Check the source system, audit policy, agent or forwarder health, network path, permissions, time range, ingestion delay, parsing, and index selection. Document the visibility gap and escalate when necessary.

**24. What is the difference between a fact and an assumption in an investigation?**  
A fact is directly supported by evidence, such as a recorded failed login. An assumption or hypothesis is an interpretation that requires further validation.

**25. Why should an analyst not immediately declare a compromise after a suspicious login?**  
A suspicious login is a signal, not proof. The analyst must validate the account, source, authentication context, authorization, and subsequent activity before reaching a conclusion.

## Final takeaway

A SOC analyst does not simply search for an Event ID or count failed logins. The analyst identifies the source of the evidence, understands what the event actually records, checks the account and asset context, correlates related activity, builds a timeline, and documents what is known and unknown.

**Remember this investigation sequence:**

1. Validate the alert.
2. Identify the affected account and asset.
3. Examine the raw events.
4. Establish the timeline.
5. Correlate related log sources.
6. Assess scope, impact, and confidence.
7. Document evidence and findings.
8. Escalate or respond according to procedure.

> **Core SOC principle:** Never treat an alert as proof. Validate the evidence, understand the context, build the timeline, and clearly separate facts from assumptions.
