# Day 09 – Threat Hunting Fundamentals

## 1. Introduction

Threat hunting is the proactive process of searching an organisation's systems, logs, and security telemetry for signs of suspicious or malicious activity that may not have triggered an existing security alert.

A SOC analyst usually investigates alerts generated by security tools. A threat hunter goes a step further by actively looking for threats that existing detection rules may have missed.

**Example:** An organisation has a SIEM rule that detects repeated failed logins. An attacker may avoid this rule by using a stolen password and signing in successfully. A threat hunter can search for unusual login locations, unfamiliar devices, or unexpected access patterns.

Threat hunting does not replace SIEM monitoring or alert triage. It complements them.

## 2. Threat Hunting vs Alert Triage

| Alert triage | Threat hunting |
|---|---|
| Usually reactive | Proactive |
| Starts with an alert | Starts with a hypothesis, question, or lead |
| Validates activity detected by a rule | Searches for suspicious activity that may not have alerted |
| Follows an existing detection | Can reveal gaps in existing detections |
| Determines whether an alert needs escalation | May discover new incidents or improve detection coverage |

Both activities are important in a Security Operations Centre (SOC).

## 3. Why Threat Hunting Is Important

Attackers may try to avoid detection by:

- Using legitimate administrative tools.
- Accessing systems with stolen credentials.
- Keeping activity below alert thresholds.
- Moving between systems using valid accounts.
- Using new malware or infrastructure not present in threat-intelligence feeds.
- Blending malicious actions with normal user activity.

Threat hunting helps analysts look beyond known signatures and existing alerts.

A hunt may also identify missing logs, weak detection rules, or areas where the organisation needs better visibility.

## 4. Main Approaches to Threat Hunting

### 4.1 Hypothesis-driven hunting

The analyst creates a testable statement about possible malicious activity and searches available data for supporting or contradicting evidence.

Example hypothesis:

"An attacker may be using PowerShell to execute commands on Windows endpoints."

The analyst can examine process creation events, command-line data, parent-child process relationships, endpoint alerts, and network activity.

A good hypothesis should be specific enough to guide a search and should identify the telemetry needed to investigate it.

### 4.2 IOC-driven hunting

An Indicator of Compromise (IOC) is an observable value that may be associated with malicious activity.

Examples include:

- IP addresses.
- Domain names.
- URLs.
- File hashes.
- File names or other identifiable artefacts.

Example hypothesis:

"An endpoint in the organisation may have communicated with an IP address reported as malicious."

The analyst searches DNS, firewall, proxy, and endpoint records for the indicator.

**Important:** An IOC match is an investigative lead, not proof of compromise. Check the reliability and age of the intelligence, the source of the match, and the surrounding activity.

### 4.3 Behaviour-driven hunting

Behaviour-driven hunting looks for suspicious actions or patterns instead of searching only for known indicators.

Examples include:

- An account logging in at an unusual time.
- A user accessing systems they do not normally use.
- Unexpected administrative activity.
- Suspicious script execution.
- Unusual outbound network connections.
- Unexpected changes to accounts or security settings.

Behaviour-based findings must be compared with normal activity and validated before being treated as malicious.

## 5. Threat Hunting Methodology

A structured hunt makes the investigation easier to explain, repeat, and review.

### Step 1 – Develop a hypothesis

Identify the behaviour you want to investigate.

Example:

"An attacker may be attempting password spraying against multiple employee accounts."

### Step 2 – Identify the required data

Determine which data sources can help answer the question.

For password spraying, useful sources may include:

- Windows Security logs.
- Active Directory domain controller logs.
- VPN authentication logs.
- Identity-provider sign-in logs.
- SIEM authentication events.

### Step 3 – Search and analyse

Search the available telemetry using appropriate filters, queries, and time ranges.

Look for patterns such as:

- Repeated failures.
- Multiple accounts targeted by one source.
- Unusual source addresses.
- Successful authentication after suspicious failures.

### Step 4 – Validate findings

Review the underlying events and surrounding context.

Ask:

- Is the activity expected?
- Is the account used by a person or service?
- Is the source address known?
- Is there evidence of a successful compromise?
- Are related endpoint or network events available?

Do not classify an anomaly as malicious without supporting evidence.

### Step 5 – Document and improve

Record the hypothesis, data sources, time range, searches, observations, and conclusion.

If the hunt identifies a useful pattern, the SOC may create or improve a detection rule so similar activity can be identified in the future.

## 6. MITRE ATT&CK and Threat Hunting

MITRE ATT&CK is a knowledge base that describes adversary tactics and techniques based on observed attack behaviour.

It helps analysts describe what an attacker may be trying to achieve and how they may attempt to do it.

| Tactic | Meaning | Example behaviour |
|---|---|---|
| Initial Access | Gaining entry into an environment | Phishing or exploiting a public-facing application |
| Execution | Running malicious code | Script or command execution |
| Persistence | Maintaining access | Creating a scheduled task |
| Privilege Escalation | Gaining higher permissions | Abusing permissions or vulnerabilities |
| Defense Evasion | Avoiding security controls | Disabling or bypassing security tools |
| Credential Access | Obtaining credentials | Credential dumping or password theft |
| Discovery | Learning about the environment | Enumerating users and systems |
| Lateral Movement | Moving to other systems | Remote access to another host |
| Collection | Gathering information | Collecting files of interest |
| Exfiltration | Removing data from the environment | Unauthorised outbound data transfer |

A hunter can use ATT&CK techniques to develop questions such as:

- What logs would show suspicious PowerShell execution?
- Which events could indicate unexpected account creation?
- What evidence might show remote access to another system?

ATT&CK provides a structured vocabulary. A technique mapping alone does not prove that an attack occurred.

## 7. Practical Threat Hunting with Splunk

The following SPL searches are educational starting points. They assume an index named `main` and example fields such as `EventCode`, `TargetUserName`, `IpAddress`, and `Computer`.

Your own data may use different field names. Inspect raw events and confirm field extraction before using these searches. Change the index and fields to match your environment.

### 7.1 Hunt for repeated failed logins

**Hypothesis:** A source may be attempting to access one or more accounts repeatedly.

Relevant Windows event: **4625 – Failed logon**

```spl
index=main EventCode=4625
| stats count as Failed_Attempts
        dc(TargetUserName) as Unique_Accounts
        values(TargetUserName) as Targeted_Accounts
        by IpAddress
| sort - Failed_Attempts
```

This search:

- Counts failed logins by source IP.
- Counts distinct accounts targeted by each source.
- Lists the targeted accounts.
- Sorts sources by the number of failures.

A source targeting many accounts may be consistent with password spraying. A large number of failures against one account may be consistent with brute-force activity. These are leads for investigation, not automatic conclusions.

### 7.2 Review successful logins

**Hypothesis:** A compromised account may be used from an unexpected source.

Relevant Windows event: **4624 – Successful logon**

```spl
index=main EventCode=4624
| table _time Computer TargetUserName IpAddress LogonType
| sort 0 _time
```

Review the account, source, destination host, logon type, and timestamp.

A successful login is not inherently suspicious. Compare it with the user's normal activity and other available evidence.

### 7.3 Look for PowerShell process execution

**Hypothesis:** PowerShell may have been used to execute unexpected commands.

Relevant Windows event: **4688 – Process creation**, when process-creation auditing is enabled.

```spl
index=main EventCode=4688
| search ProcessName="*powershell.exe*"
| table _time Computer TargetUserName ProcessName
| sort 0 _time
```

Investigate:

- Whether the user normally runs PowerShell.
- Whether the host is an administrative workstation or server.
- The parent and child processes.
- Command-line arguments, if collected.
- Related file and network activity.

Process command-line details require suitable audit configuration and collection. The field name may differ in your data.

### 7.4 Look for newly created accounts

**Hypothesis:** An unauthorised account may have been created to maintain access.

Relevant Windows event: **4720 – User account created**

```spl
index=main EventCode=4720
| table _time Computer TargetUserName
| sort 0 _time
```

Check whether the account creation was approved. Inspect the raw event to identify both the account created and the account that performed the action; those identities may be stored in different fields.

### 7.5 Review security group changes

**Hypothesis:** An account may have been added to a privileged group unexpectedly.

Relevant Windows events include:

- 4728 – Member added to a global security group.
- 4732 – Member added to a local security group.

```spl
index=main (EventCode=4728 OR EventCode=4732)
| table _time Computer EventCode TargetUserName
| sort 0 _time
```

Review the group name, affected member, actor, and reason for the change. Inspect the raw event because the exact field names and meanings depend on the event.

### 7.6 Compare activity over time

A single search over a short period may not show whether an activity is unusual. Compare the current activity with an appropriate historical baseline.

For example, examine successful logins by account and source over a suitable time range:

```spl
index=main EventCode=4624
| stats count as Login_Count by TargetUserName IpAddress
| sort - Login_Count
```

This is only a summary. It does not automatically identify unusual locations or behaviour. A meaningful baseline needs sufficient historical data and appropriate context.

## 8. Threat Hunting on Linux Systems

Linux authentication and system logs can provide useful information for hunting.

Common log locations include:

| Location | Purpose |
|---|---|
| `/var/log/auth.log` | Authentication messages on many Debian-based systems |
| `/var/log/secure` | Authentication messages on many Red Hat-based systems |
| `/var/log/syslog` | General system messages on many Debian-based systems |
| `/var/log/messages` | General system messages on some distributions |
| systemd journal | System and service logs queried with `journalctl` |

The actual location depends on the distribution and logging configuration.

### Review SSH authentication failures

On systems that use `/var/log/auth.log`:

```bash
sudo grep -i "Failed password" /var/log/auth.log
```

This searches for SSH authentication failure messages.

### Review SSH service logs

```bash
sudo journalctl -u ssh --since "24 hours ago"
```

The service may be named `sshd` instead of `ssh` on some distributions.

### Review recent authentication records

```bash
sudo journalctl --since "24 hours ago" | grep -iE "authentication|session|sudo|failed"
```

Use the results as leads. Confirm the account, source, host, timestamp, and surrounding activity before drawing conclusions.

## 9. From Threat Hunting to Detection Engineering

Threat hunting and detection engineering support each other.

Example:

1. A hunter investigates unexpected PowerShell activity.
2. The search identifies a suspicious pattern.
3. The analyst validates the pattern using endpoint and authentication evidence.
4. The SOC develops a detection rule for the behaviour.
5. The rule is tested against relevant data and tuned.
6. Future matching activity can generate an alert for investigation.

A successful hunt may therefore improve the organisation's ability to detect similar activity in the future.

Not every hunt produces a confirmed incident. A hunt may also identify normal activity, insufficient data, or a detection gap. These are useful findings when documented accurately.

## 10. Common Threat Hunting Mistakes

- Starting a hunt without a clear question or hypothesis.
- Assuming every unusual event is malicious.
- Treating an IOC match as proof of compromise.
- Ignoring missing or incomplete telemetry.
- Using incorrect field names or an unsuitable time range.
- Failing to compare activity with normal behaviour.
- Assuming that events are related only because they occurred close together.
- Making conclusions that are not supported by evidence.
- Failing to document the searches and findings.
- Not sharing useful detection gaps with the detection engineering team.

## 11. SOC Interview Questions and Answers

### 1. What is threat hunting?

Threat hunting is the proactive process of searching an organisation's systems and security telemetry for potential threats that may not have been identified by existing detections.

### 2. What is the difference between threat hunting and alert triage?

Alert triage begins with an alert and validates the activity that triggered it. Threat hunting begins with a hypothesis, question, or lead and searches for suspicious activity that may not have generated an alert.

### 3. What is hypothesis-driven hunting?

It is an approach where an analyst develops a testable statement about possible malicious activity and searches available telemetry for supporting or contradicting evidence.

### 4. What is IOC-driven hunting?

It is the process of searching logs and telemetry for known indicators such as malicious IP addresses, domains, URLs, and file hashes.

### 5. What is behaviour-driven hunting?

It focuses on suspicious actions or patterns, such as unusual login behaviour, unexpected administrative activity, or suspicious process execution, rather than relying only on known indicators.

### 6. Why is MITRE ATT&CK useful in threat hunting?

It provides a structured knowledge base of adversary tactics and techniques. Analysts can use it to develop hunting hypotheses, describe observed behaviour, and identify detection coverage gaps.

### 7. Does an IOC match confirm a security incident?

No. It is an investigative lead. The analyst must validate the indicator, its source and reliability, and the surrounding activity.

### 8. What happens after a successful hunt?

The analyst documents the findings, escalates any suspected incident according to procedure, and may recommend new or improved detection rules.

### 9. Can threat hunting identify unknown threats?

It can identify suspicious behaviour without relying on a previously known file hash or signature. The findings still need investigation and validation.

### 10. What information should be recorded in a hunt?

Record the hypothesis, scope, time range, data sources, search queries, observations, evidence, limitations, conclusion, and recommended follow-up.

## 12. Quick Revision Notes

- Threat hunting is a proactive search for potential threats.
- Alert triage is generally reactive and begins with an alert.
- Hypothesis-driven hunting starts with a testable question.
- IOC-driven hunting searches for known indicators.
- Behaviour-driven hunting looks for suspicious patterns.
- MITRE ATT&CK helps describe adversary tactics and techniques.
- Splunk SPL can search and summarise security telemetry.
- An unusual event or IOC match is not automatically proof of compromise.
- Validate findings with context and supporting evidence.
- Document the hunt and share useful detection improvements.
